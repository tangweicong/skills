## 用户输入（本轮）

> 图谱的初始想法是因为，我现在在用这套流程做一个 AI 生成小说的项目，我在尝试过程中发现图谱的必要性，所以在想是不是可以把图谱加入到这个流程中作为通用能力，主要的流程还是希望保持 AI 自动维护为主，人工审核为辅。你看看这个是否够得上痛点，避免撞 YAGNI

**新事实三点**：① 真实驱动 = **正在用 proj-* 跑一个 AI 生成小说项目**；② 痛点 = 尝试中**实际撞到**图谱缺失（非理论推演）；③ 期望维护模型 = **AI 自动维护为主、人工审核为辅**。

## 重大重定位（先纠偏 · 否则后续跑偏）

round 17 我把"图谱"框成 **元层决策图谱**（proj-* 自己的 `INV/ORD/EXP` 溯源图，L0/L1/L2）。但你的真实需求是 **领域知识图谱**——被管理项目（这部小说）的**内容世界**：人物、关系、地点、时间线、设定/规则、伏笔与回收、连贯性约束。两者必须分开：

| | 元层图谱（round 17）| **领域图谱（本轮 · 你的真实需求）** |
|---|---|---|
| 图的对象 | proj-* 的决定/来源/废止边 | 小说的人物/关系/时间线/设定/伏笔 |
| 数据来源 | 已隐含在 DECISIONS（零作者派生）| 随生成**新产生**（需 AI 抽取/维护）|
| 维护模型 | 派生（改 DECISIONS 即更新）| **AI 自动抽取 + 人审**（你的要求）|
| 价值 | 低（散文已能读）| **高（长篇连贯性是硬痛点）** |
| YAGNI | 对本仓库 YAGNI | **不撞 YAGNI（见下）** |

→ round 17 的 L1「派生」结论 + 候选 ORD-35「零作者派生原则」**只适用元层图谱**，**不**适用领域图谱（领域图谱必然是"被生成/被抽取"的，能量模型完全不同）。本轮据领域图谱重写候选。

## 事实与假设

### 已查证事实（领域图谱在 AI 长篇生成中的痛点与标准解法 · 全部带 URL）

- **F1 · 长篇 AI 生成连贯性是公认硬痛点**：上下文窗口装不下整本书，模型会忘记/矛盾既定事实（人物眼睛颜色翻页就变、死人复活、时间线打架）。标准缓解 = **故事圣经 / 知识图谱 + 检索 grounding**。多个开源/商业系统专门解决此问题（下列）。
- **F2 · 标准解法形态高度一致**——「**结构化状态在散文之外作为 source of truth** + AI 每章后按 output contract 吐机读更新（JSON/YAML）+ 确定性连贯检查先于 LLM + 人在审美点审核」：
  - **Novel OS**：多 agent，"每个 agent 结构化输出被解析合并进中央 JSON state"，确定性连贯引擎（休眠线索/未回收伏笔/时间线漂移）**先于** LLM Guardian 跑。[Novel-OS](https://github.com/mrigankad/Novel-OS)
  - **postwriter**："数据库是 source of truth 而非散文"，5 硬校验器（连贯/时间线/POV/知识状态/禁用模式）gate 接受 + 10 软评分；"先局部修再全局重写"。[postwriter](https://github.com/avigold/postwriter)
  - **SAGA**：用 **Neo4j 知识图谱**存 canon（人物/地点/关系/事件），两阶段生成+校验（关系/特征一致性、矛盾检测、图自愈去重）。[SAGA](https://github.com/Lanerra/saga)
  - **graphify-novel**：区分两层——`bible/`（**状态层**：X 现在在哪）vs 抽取的**图层**（X 与 Y 怎么关联起来的、跨章查询、结构枢纽、隐含矛盾）；"二者不互相替代"。[graphify-novel](https://github.com/Anshler/graphify-novel)
  - **NovelCrafter Codex**：结构化 wiki 式数据库，自动索引每次提及 + Progressions（状态随时间演化）+ 作为 source of truth 注入 AI 上下文。[Codex](https://www.novelcrafter.com/features/codex)
- **F3 · 两个关键工程约束**（同样来自上述实践）：
  - **output contract 防幻觉持久化**：必须让 LLM 返回**机读 state 更新**，否则幻觉改动会污染圣经。[Novel-OS / postwriter]
  - **读前要选择性、控预算**：NovelCrafter 明示"只放本次请求必需的信息，避免 info 过多反而confuse AI"——即**读前 grounding 要按需取相关子图**（GraphRAG local search），非全图灌入。[Codex] + round 17 F3 [GraphRAG]

### 推理（三元组标注）

- **推理 · proj-experts · 等价性/Bertalanffy 视角**：F2 的标准形态——「**散文外的结构化 source of truth + AI 自动维护 + 确定性校验先于 LLM + 人在关键点审**」——与 proj-* 既有纪律**几乎逐条同构**：DECISIONS=source of truth（proj-shape）/ ORD-26 自动生成+人 GATE / ORD-22 三类 validation gate（确定性 structural+lint 先于 behavioral）/ verifier≠maker / ORD-34 人供给必要多样性 / INV-01 人只读 ≤N。**这强烈说明领域图谱不是异类新机制,而是把已有模式套到"领域内容"上**。依据 F2 + DECISIONS ORD-22/26/34。
- **推理 · proj-experts · YAGNI 判定**：YAGNI 反的是**投机**抽象（为想象需求先建）。本例**痛点真实、已撞、有十余个专用工具佐证标准解法** → **不投机** → 不撞 YAGNI（对"领域图谱能力"本身）。依据 F1/F2 + 用户"尝试中发现"。
- **推理 · proj-experts · 最小先行/Prigogine 视角**：领域图谱是**被生成**的（authored/AI-extracted），不能套 round 17"零作者派生"原则；但它的维护能量是**生产性的**（防的是后期昂贵的连贯 bug 返工），AI 自动维护 → 人力能量低 → **净正**。且 graphify-novel/Novel OS 都显示可**最小先行**：先做「状态层 + 确定性连贯检查」（便宜、覆盖大部分痛点），重「抽取图层」（跨章关系查询）后加。依据 F2 graphify 两层 + F3。

### 待验证 / 未查证

- **U1（假设需确认）**：我假设你说的"图谱" = **故事连贯性领域图谱**（人物/关系/时间线/设定/伏笔）。若你指的是别的（如剧情因果推演图、世界观地图可视化），请纠正。
- **U2**：能否从**一个领域（小说）**就把它抽象成 proj-* 的**通用能力**？按等价性纪律，单路径不证通用终态——通用化宜在**小说证成 + 第 2 个领域**出现同形需求后再做（否则会把小说专属假设烧进"通用"接口）。
- **U3**：小说项目当前规模（章数/人物数）与**具体撞到的连贯失败类型**未知——决定该先做"状态层+检查"还是需要重"抽取图层"。

## 方法专属输出（proj-experts · 3 视角）

### 视角 A · AI 小说工程实践者（Novel OS / SAGA / graphify / NovelCrafter）

**【已公开立场】**：散文外结构化 state = source of truth；AI 每章 output contract 吐机读更新；确定性连贯检查先于 LLM；状态层 vs 抽取图层两分 [F2]。
**【模拟推理】**：你的需求是这条成熟赛道的正中靶心，**不需要从零发明**。最小可用 = 状态层（人物/地点/伏笔的当前真相 JSON/YAML）+ 4–5 个确定性检查（时间线漂移/未回收伏笔/特征矛盾/死亡复活/知识状态）。重图层（Neo4j 式跨章关系查询）按需后加,别一上来就 SAGA 全套。

### 视角 B · 流水线等价性（Bertalanffy）

**【已公开立场】**：等价性——不同领域殊途同归到同一结构 [GST]。
**【模拟推理】**：领域图谱所需的机制 proj-* **已有八成**——source of truth（DECISIONS 模式）、自动+人 GATE（ORD-26）、确定性校验先于 LLM（ORD-22 三类 gate）、output contract（proj-run 5 字段闭环）、读前控预算（INV-01/Shannon）。新增的只是 **(a) 一种"领域知识 artifact"类型 + (b) 一组连贯性检查**。这意味着进 proj-* 的**增量小、风险低**——是"接线+命名"而非造新机制（类比 ORD-27/31）。

### 视角 C · 极简 / YAGNI 守门人

**【已公开立场】**：反过早抽象；通用抽象需 ≥2 实例 [rule #2]。
**【模拟推理】**：两件事要分开判 YAGNI——① **给这部小说做领域图谱** = 不撞 YAGNI（真痛点，立刻做）；② **把它抽象成 proj-* 通用能力** = **仍有 YAGNI 风险**，因为只有 1 个领域样本（U2）。建议：先在小说项目把它跑通跑顺（dogfood），**通用化作为被门控的后续**（小说证成 + 第 2 领域同形需求）。否则"通用接口"会偷偷烧进小说专属假设。

## 讨论

### 1. YAGNI 判定（直接回答你的问题）

- **领域图谱能力本身**：✅ **不撞 YAGNI**。痛点真实已撞、业界标准解法成型（F1/F2 十余工具）、与你"AI 维护+人审"诉求完全吻合（F2 正是该最佳实践）。
- **"AI 自动维护为主、人工审核为辅"**：✅ 不仅兼容，**正是文献最佳实践**（output contract → 解析合并 → 确定性检查 → 人在审美点审），且对齐 proj-* 的 INV-01 / ORD-26 / ORD-34。
- **唯一要按住的**：把它**一步到位做成 proj-* 通用子系统**仍有过早抽象风险（U2 单领域）。→ 解法见下"分两步"。

### 2. 分两步（避免过早抽象,又不耽误真实痛点）

| 步 | 做什么 | 在哪 | 门控 |
|----|--------|------|------|
| **步 1（现在）** | 给**这部小说**建领域图谱能力：状态层（人物/地点/伏笔现状）+ 确定性连贯检查 + AI 每章 output-contract 更新 + 人 GATE 审 | 小说项目（用 proj-* 跑）| 真实 dogfood = EXP-09 |
| **步 2（被门控的后续）** | 若步 1 证成 + 出现第 2 个领域同形需求 → 把"领域知识 artifact + 连贯检查"抽象进 proj-*（候选落点：proj-survey 引导生成 baseline 图 / proj-run 把连贯检查作 behavioral gate / proj-shape 定 artifact schema）| proj-* skills | 步 1 成功 + U2 第 2 领域 |

> 关键：**步 1 不需要等 proj-* 改任何 skill**——它复用现有 ORD-22/26/34 机制在小说项目里就能跑。proj-* 的改动（通用化）留到步 2，证据充分再动。这既正面回应你的痛点，又不违反项目反过早抽象纪律。

### 3. 最小先行（即便步 1 也别一上来上重图）

按 graphify-novel 的两层分（F2）：**状态层 + 确定性检查**先做（便宜、覆盖"眼睛变色/死人复活/伏笔丢失/时间线乱"等高频失败）；**抽取图层**（跨章"X 与 Y 怎么连上的"关系查询、结构枢纽）作为步 1 内的可选增量，按你真实撞到的失败类型（U3）决定要不要。

### 4. 与 round 17 的关系

round 17 的元层 L1 派生图（proj-* 自己的决策图）**与本轮领域图谱正交**——前者低优先 nice-to-have,后者是真痛点。本轮**不**否定 round 17,只是把"通用能力"的真实所指从元层切到领域层。round 17 候选 ORD-35（零作者派生原则）降为**仅约束元层图谱**的可选项;本轮 ORD-35 改写为领域图谱定位（见下）。
