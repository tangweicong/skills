### 已查证事实

**外部**（三视角各自独立检索 · 来源基本不重叠 · 原文见 `docs/pmo/j4-spike/`）：

- **F1 · ADR 的真实存活曲线很差**——挖掘 GitHub 1,267 个仓库、5,000+ 条 ADR：**超过 50% 采用 ADR 的仓库只有 1–5 条记录**，作者解释为「尝试过但未真正采纳」。[DOI:10.1109/ACCESS.2023.3287654](https://doi.org/10.1109/ACCESS.2023.3287654)（红队 · 已核验 DOI 解析）
- **F2 · 长上下文可靠性随长度下降**——18 个前沿模型实测：输入越长可靠性越差，**即便任务简单如检索与复制**；干扰项存在时进一步下降。[Chroma Context Rot](https://research.trychroma.com/context-rot)。Anthropic 表述为「注意力预算」：上下文是有限资源、边际收益递减，须**策展而非最大化**。[Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（红队）
- **F3 · 字段是单向棘轮**——「**一旦字段投入使用，就没有轻松的路径去减少它们**」，建议每个新字段先做必要性评审 + 季度审计。[Atlassian 治理文档](https://success.atlassian.com/solution-resources/agile-and-devops-ado/agile-at-scale-practices/jira-custom-fields-governance)（红队）
- **F4 · 连 MADR 都把 status 标为可选，且无 blocked-on 字段**——MADR 4.0.0 模板原文首行注释：`# These are optional metadata elements. Feel free to remove any of them.`；全模板**没有** `blocked-on` / `depends-on`。[MADR 4.0.0 模板原文](https://raw.githubusercontent.com/adr/madr/4.0.0/template/adr-template.md)（视角 A **主动报告对己不利的发现**）
- **F5 · ADR 索引纪律 = 目录不是摘要**——「保持它是 table of contents（编号/标题/状态/日期/链接）；**避免把 ADR 的叙事复制进索引**」。[mdedit.ai](https://mdedit.ai/blog/ai-assisted-adrs-in-markdown)（博客级，视角 A 已自标证据等级）
- **F6 · Kanban 官方：要的是「如何控制 WIP」+ 例外须显式化**——工作流定义 6 项最低必需中含「一份关于 WIP 将如何被控制的定义」（措辞是**如何控制**不是**限制设为几**）、「工作项如何流经每状态的显式策略」、「**任何对 WIP 控制的可接受例外都必须被显式化**」；四流度量之一 = **Work Item Age**。[Kanban Guide](https://kanbanguides.org/english/)（视角 A）
- **F7 · DRY 的正式表述覆盖文档，且给出解法形状**——「每一条知识都必须在系统中有单一、无歧义、权威的表示」[DRY](https://en.wikipedia.org/wiki/Don%27t_repeat_yourself)；Dave Thomas 原话：「…**这些让你拥有单一的权威表示，再由它生成非权威的工作产物**」。[Artima 访谈](https://www.artima.com/articles/orthogonality-and-the-dry-principle)（视角 B）
- **F8 · 文档腐坏是结构问题不是纪律问题**——「那条链接是缺陷本身：它是手工的、不是任何人明确的职责、并且**静默失败**」[paelladoc](https://paelladoc.com/blog/living-documentation/)；「文档衰减不是纪律失败，是数学问题……**拥有优秀文档卫生的团队照样有过期的架构图**」[kognita](https://www.kognita.co/blog/codebase-documentation-always-out-of-date)（博客级，视角 B 已自标）
- **F9 · 轻结构约定可支撑零维护派生**——Conventional Commits 的全部要点 = 「在提交消息上加一层轻量约定，**使其易于在其上编写自动化工具**」，首条收益即「**自动生成 CHANGELOG**」。[v1.0.0 规范](https://www.conventionalcommits.org/en/v1.0.0/)（视角 B）

### 推理（非事实、非待验证）

- **推理 · 模拟推理 · 红队（Shape Up/YAGNI 谱系）**：ORD-32 引入的机读块**自己变成了散文垃圾场**——这不是「schema 不够细」的证据，是「schema 不是绑定约束」的证据；且 solo maintainer 场景下 F1 里的「谁能强制执行」答案是**没有人**；依据 [F1](https://doi.org/10.1109/ACCESS.2023.3287654) + [dantleech](https://www.dantleech.com/blog/2024/03/10/why-i-dont-write-adrs/)。
- **推理 · 模拟推理 · 视角 A（ADR/Kanban 传统）**：`status` 之所以 1195 字符**不是因为缺字段，是因为它被当成了摘要而不是索引**；ADR 传统的贡献不是「多给几列」而是「**规定这一栏只准放什么**」（**类型界**）；依据 [F5](https://mdedit.ai/blog/ai-assisted-adrs-in-markdown)。另：图谱线停在 r18、当前 r33 → **Work Item Age = 15 轮**，这个数字**系统内任何地方都不存在**，而它正是「什么卡住了」的直接答案；依据 [F6](https://kanbanguides.org/english/)。
- **推理 · 模拟推理 · 视角 B（DRY/单一真相源）**：`status` 里每条信息在别处**都已有权威表示**（轮次结论在 `NN-*.md`、决定在 §普通决定、实验在 §待验证尝试与 `pending_exp`、时序在 §变更日志与 git）→ 它是一份**被手工维护的非权威工作产物**，Thomas 的处方不是「给副本加 schema」而是「**让副本被生成**」；依据 [F7](https://www.artima.com/articles/orthogonality-and-the-dry-principle)。
- **推理 · 父 agent 综合（本文档，非任一视角原话）**：F-int2 为争议轮 §收敛 1（「ORD-32 不是失败是不完整」）补上**机制层解释**，并对 §分歧 3（长度界 vs 类型界）构成**部分裁决**——存活下来的那条约束（≤12 行）**恰恰就是一条长度/计数界**，说明长度界并非天然会被规避；前提是它**出现在使用点且可一眼判定真假**。→ 支持「两者都要」而非二选一。

#### 收敛（【模拟推理】，非任一专家原话 · 与上表 4 行分歧**并存**，不取代之）

1. **ORD-32 没有「失败」，它是「不完整」**——给一个容器（≤12 行摘要）设了界，却把相邻容器（`status`）留成无界的，**压力全部迁移到唯一没有上限的槽位**。熵没有被消散，只是搬了家。三方独立得出，**且与父 agent 的 git 实测（F-int1/2）第四次独立收敛**——本轮最硬的结论。
2. **只给「形状」不给「界」，等于再搬一次家。** 无论线程表还是派生块，若不同时约束「什么能进去」，四行表会在十轮后变成四行长散文。
3. **`status` 当前装的是叙事，而叙事在别处已有权威副本**——它应当只是索引。
4. **任何方案都必须留在 `DECISIONS.md` 内部**——INV-01 的 ≤5 上限不容动用；三方无一提议新增人读文件。

## 讨论

### 1. 三条独立路径 + 一份内部数据，指向同一个诊断

本轮最强的结果不是任何一条建议，而是**四条互不相通的路径收敛到同一句话**：

| 路径 | 说法 |
|------|------|
| 红队（ADR 存活率 + 上下文工程）| 「ORD-32 定了约定却没定检查——≤12 行那条活下来了，`status` 那条死了；区别在**一个是肉眼可见的溢出，一个是不可见的溢出**」|
| 视角 A（ADR 索引纪律）| 「`status` 是 1195 字符不是因为缺字段，是因为**它被当成了摘要而不是索引**」|
| 视角 B（DRY）| 「`status` 是一份**被手工维护的非权威工作产物**，每条信息在别处都有权威副本」|
| **父 agent git 实测（三视角看不到）** | 「同一条决定的两半，**可数数字写在使用点的活了 51 天，定性措辞写在别处的涨了 4.21 倍**」|

**四路收敛 = 诊断可信度高**。而这四路的**处方不同**，那才是分歧所在。

### 2. 两条必须由你裁决的（其余可由数据或规则定）

- **D1 · 图谱线是 paused 还是 stale？** 这条线停在 round 18，现在 round 33，**Work Item Age = 15 轮**。这个数字目前**系统里任何地方都不存在**。它是一个**单实例判决**：你若答不出，说明「声明含意图」这个论据在本项目不成立（B 胜）；你若答得出、且答案与「机器按停滞轮数派生的候选状态」不同，说明派生会漏真信息（A 胜）。
- **D4 · 执行侧有没有真症状？** 双方都同意加 Work Item Age 度量（近零成本、可派生）。分歧只在**要不要设 WIP 上限 + 写中断协议**。裁决判据很干脆：**你有没有实际观察到「同时开太多线导致每条都推不动」？** 没有症状则 JIT + YAGNI 共同要求不设。

### 3. 我对 D3 的补充裁决（基于三视角拿不到的数据）

红队在揭示轮向 A 让步、承认「类型界更强、长度界会被规避」。**但 F-int2 显示这个让步让过头了**：ORD-32 里**存活下来的那条约束（≤12 行）恰恰就是一条长度界**，它 51 天零违反。所以长度界**并非天然会被规避**——前提是它**写在使用点上且可一眼判定真假**（这正是失败的那半所缺的：定性措辞 + 写在别处）。

**→ 建议 D3 取「两者都要」**：类型界管「什么能进去」，长度界管「进去多少」，且**两条都必须写在 yaml 块紧邻处 + 进 validator**。这也正好是三视角 Step 6 的落点，只是理由更硬。

### 4. 三视角一致反对、值得单独标出的一条

**不要只加表结构而不加机器检查。** 红队把它写成了一条**可证伪预测**：「若机器检查未落地而仅落地表结构，则 **6 个月内复发第三次**」。这条应当登记为 EXP（见下），它给本次修复一个**可验收的停止信号**，而不是又一句「刻意不再扩写」的自注。
