## 事实与假设

### 轻量框定（查证前问题）

| # | 问题 | 查证结论（摘要）|
|---|------|------|
| Q1 | 决策记录本身是否已构成图？业界怎么做？ | ADR（Nygard 2011）：决定即图——status + **双向 typed 链接**（Supersedes/Amends/Extends/Depends on/Relates to）；ID 顺序不复用；废止决定留存为历史；工具从 frontmatter 链接**派生** Mermaid/DOT 图 [F1] |
| Q2 | 「来源/溯源」边有没有标准模型？ | W3C PROV：entity/activity/agent + `wasDerivedFrom`/`wasRevisionOf`/`wasAttributedTo`；区分 precise/imprecise derivation [F2] |
| Q3 | 「图谱喂 agent / 通用知识图谱」前沿做法与代价？ | Microsoft GraphRAG：LLM 抽取 KG 支持 global/multi-hop 查询，但 indexing **明确昂贵**（大量 LLM 调用）、"start small"、生产需 graph db + 与向量 RAG 混合 [F3] |

### 已查证事实

- **F1 · ADR 决策日志即图**（Nygard 2011 / Fowler）——决定带 status，被替代时**保留并标 superseded + 双向链接**到新决定；ID 顺序、不复用；README 维护索引；`adrs` 工具把链接存 YAML frontmatter 并**生成 Mermaid/DOT** 依赖图。[cognitect](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) / [Fowler](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html) / [adrs link 类型](https://joshrotenberg.com/adrs/commands/link.html)
- **F2 · W3C PROV 溯源模型**——标准词汇 entity/activity/agent + `wasDerivedFrom`（含子关系 `wasRevisionOf`/`wasQuotedFrom`）+ `wasAttributedTo`；支持「精确/不精确派生」两档。[PROV-DM](https://www.w3.org/TR/prov-dm/) / [PROV-O](https://www.w3.org/TR/prov-o/)
- **F3 · GraphRAG（Microsoft Edge et al. 2024）**——LLM 自动从非结构化文本抽 KG + 社区层次摘要，answer global/「跨语料主题」类查询优于朴素向量 RAG；**但 indexing 计算昂贵（多次 LLM 调用）**，官方警告 "start small"，生产级需 Neo4j 等 graph db + 向量混检。[GraphRAG docs](https://microsoft.github.io/graphrag/) / [MS Research blog](https://www.microsoft.com/en-us/research/blog/graphrag-new-tool-for-complex-data-discovery-now-on-github/)

### 推理（三元组标注）

- **推理 · proj-experts · ADR/Nygard 视角**：本项目 `DECISIONS.md` 已是 **ADR 式决策日志**——`INV/ORD/EXP` = 顺序不复用 ID，「来源」≈ 链接，变更日志「废止/修订/落实」≈ supersedes/derived 边。故"加图谱"在多数解读下 = 把**已隐含的 typed edge 显式化 + 派生视图**，而非造新数据。依据 [ADR superseded/links](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html) + [adrs 派生图](https://joshrotenberg.com/adrs/commands/link.html)。
- **推理 · proj-experts · PROV 视角**：项目「来源」字段 ≈ `wasDerivedFrom`(轮次→ORD) + `wasAttributedTo`(用户/agent)。可借 PROV 词汇规范化以**机验来源完整性**（接 C4），但**过度本体化（RDF/三元组库）违简约** → 只取轻量子集。依据 [PROV-DM](https://www.w3.org/TR/prov-dm/)。
- **推理 · proj-experts · GraphRAG 视角**：若目标是"图谱喂 agent 做 global 查询"，KG 是真增量**但 indexing 贵**；本项目决定语料**小且已结构化**（单文件 DECISIONS），现有「先读 DECISIONS / grep」已覆盖检索 → KG 检索对**本仓库** YAGNI；仅当**被管理项目语料大 + 多跳查询痛点真实**才值。依据 [GraphRAG cost caveat](https://microsoft.github.io/graphrag/)。
- **推理 · proj-experts · Prigogine/收敛 3 视角**：任何新结构 = 维护能量。**仅「从既有结构化记录零作者派生」的图是净降熵**；手工维护或 LLM 抽取的**平行** KG 是加熵 → 与 round 13 收敛 3「降低维持有序能量」直接矛盾。依据 `13-…md` §收敛 3。

## 方法专属输出（proj-experts · 4 视角）

> 各视角取互补轴；理论/实践原理标【已公开立场】（带 URL），应用到 proj-* 标【模拟推理】。

### 视角 A · ADR 决策日志实践者（Nygard / Fowler）

**选用理由**：本系统本质是决策日志，最懂"决定如何成图"的就是 ADR 传统。
**【已公开立场】**：决定即图——typed 双向链接 + superseded 历史 + 从链接派生 Mermaid/DOT [F1]。
**【模拟推理】**：本项目**已 ~90% 是 ADR**，只差两点——(1) edge **类型未显式**（"来源"混装了 derived/supersedes/depends-on 多种语义）；(2) 没有**派生视图**。补这两点是**成熟、廉价、增量**的事，且与 ORD-33 的 C4 解析器同源。但要诚实：增量**不大**，因为散文已能读。

### 视角 B · W3C PROV 溯源建模者

**选用理由**：动机含"一致性校验"，溯源边的形式化正是 PROV 的领域。
**【已公开立场】**：`wasDerivedFrom`/`wasRevisionOf`/`wasAttributedTo` 标准词汇 [F2]。
**【模拟推理】**：把「来源」拆成 PROV 风格 typed edge，可让 C4 从"ID 存在性"升级到"**来源边完整性 + 无悬空/无孤儿/无循环**"——这是真价值。**但警惕过度形式化**：RDF/本体/三元组库对一个单文件决策日志是杀鸡用牛刀，取 `derived/supersedes/depends/verifies` 四类轻量边即可。

### 视角 C · GraphRAG / KG-for-agents（Microsoft Edge et al.）

**选用理由**：用户说"通用能力、可能喂更多应用"，对应 KG 喂 agent 上下文这条最前沿但最贵的路。
**【已公开立场】**：LLM 抽 KG 支持 global/multi-hop 查询，**但 indexing 昂贵、start small、生产需 graph db** [F3]。
**【模拟推理】**：对**本仓库**（小、已结构化）→ KG 检索 YAGNI，grep + 读全文已够；对**大型被管理项目**（几百决定 + 多 artifact + 多跳"为什么当初这么定"查询）→ KG 才显价值。结论：这是**有条件的未来选项**，不是当下必要项；且即便要，也应**从结构化记录派生**而非 LLM 重抽（省 indexing 成本）。

### 视角 D · 项目自身极简 / 耗散结构（Prigogine 收敛 3 + rule #2）

**选用理由**：需要一位守门人对"通用能力"这种大词做反过早抽象的压力测试。
**【已公开立场】**：耗散结构靠能量维持有序；降低维持能量是最高杠杆 [round 13 收敛 3]。
**【模拟推理】**：「**通用图谱子系统**」是典型投机抽象——为想象中的应用先建结构，违 rule #2 + 反过早抽象。唯一净降熵的形态 = **派生图**（零额外作者负担，改 DECISIONS 即自动更新）。且项目有铁律先例：每个能力都先 **dogfood EXP 证**（EXP-05/06/07/07b/08）再转正——图谱也该如此，不能跳过直接定"通用"。

## 讨论

### 1. 把模糊的"图谱"重构成三层（细化的关键）

| 层 | 是什么 | 维护能量 | 现状 |
|----|--------|----------|------|
| **L0 · 图谱数据** | 决定/来源/废止边**已隐含**在 IDs + 来源 + 变更日志里 | 0（已付）| **已存在** |
| **L1 · 派生图视图** | 从既有记录**自动派生** typed-edge 图 → ① Mermaid 供 viz ② json edges 供查询/影响分析 ③ 新 lint（悬空/孤儿/循环边）| ≈0（派生，复用 C4 解析器）| 未做 |
| **L2 · 通用图谱子系统** | 每项目/每阶段**维护**KG（手工或 LLM 抽取）喂检索/agent | 高（indexing/同步/graph db）| 未做 · YAGNI |

**用户说的"通用能力"语感偏 L2**；但三视角（A 廉价但增量小 / C 贵且有条件 / D 反投机）合起来指向：**真正值得现在做的是 L1，L2 是有前提的未来选项**。

### 2. 必要性逐动机核对

| 动机 | 满足它需要哪层 | 必要性 |
|------|----------------|--------|
| A 导航/影响分析（改 ORD-X 牵连谁）| **L1**（反向遍历 derived/depends 边）| **中**（34 ORD 已有痛点苗头，散文查依赖渐难）|
| B 可视化/讲解 | **L1**（派生 Mermaid）| 中低（nice-to-have）|
| C 一致性校验增强 | **L1**（边完整性 lint，**ORD-33 C4 已开头**）| **中**（低增量、同源，顺手）|
| "其它/喂 agent global 查询" | **L2** | **低 / 待真实大项目**（U2）|

→ **三个明确动机 L1 全覆盖**；只有最模糊的"喂 agent"才需 L2，而那条 YAGNI + 待数据。

### 3. 诚实的必要性结论

- 作为**当下就建的 L2 通用子系统** → 必要性**低**：投机抽象、加熵、无真实大项目痛点佐证（违 rule #2 + 收敛 3 + U2）。
- 作为**从既有记录零作者派生的 L1 视图/lint** → 必要性**中、杠杆高、能耗≈0**：覆盖全部明确动机、复用 C4 机制、符合"派生即降熵"——**值得用一条 dogfood EXP 先证**。
- L2 不否决，但**降级为"L1 验证通过 + 真实大项目痛点出现"后再议**的条件选项。

### 4. 推荐路径（不替用户拍板）

先做 **L1 dogfood**（EXP-09）：写一个从 `DECISIONS.md` + 轮次文件**派生** typed-edge 图的脚本（复用 ORD-33 的 ID/同步解析），产出 Mermaid + json edges + 三类边 lint；在**本仓库**验证它是否真揭示依赖/supersession 结构、是否支持"改 X 牵连谁"、维护能量是否真≈0。证了再谈是否泛化进 proj-shape/plan（覆盖 docs/pmo 的 WBS/manifest 边）成为"派生能力"，以及是否值得 L2。
