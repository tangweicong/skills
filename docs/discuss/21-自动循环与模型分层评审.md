### 推理（非事实、非待验证）

- **推理 · 模拟推理 · Addy Osmani（loop engineering）**：proj 的 loop 五要件（trigger/goal/tools/verification/memory）里最弱的是 **trigger**——当前唯一 trigger 是「用户在会话里发请求」，没有接 scheduler/事件源；而 memory（DECISIONS `pipeline-state` + artifacts）恰好已是**外置持久状态**，这意味着「断点再入」的地基已打好，缺的只是无人值守的触发与恢复接线；依据 [Loop Engineering](https://addyo.substack.com/p/loop-engineering) 的 loop 五要件框架。
- **推理 · 模拟推理 · Aider/Paul Gauthier（architect-editor 模式）**：model-tier 的经济性对「执行层能用什么便宜模型」极敏感；EXP-04 时代 Cursor 只能 dispatch Composer Fast（F1 失败模式的前提），Cursor 3.3 后可 pin 任意可用 model——**EXP-04 的 cost 结论前提已变，值得在同等或更大 baseline 上复测**；依据 [Aider architect blog](https://aider.chat/2024/09/26/architect.html) 的双模型分工经济性论证 + 本轮 F1/F2。
- **推理 · 模拟推理 · Karpathy（autonomy slider）**：「自动循环运行项目」不该被理解为「去掉 GATE」；正确形态是**异步 GATE**——自动臂跑到 GATE 停下、把待批事项落成 artifact + 通知、人异步批准后自动续跑。滑杆从「人陪跑」推到「人异步值守」，而不是推到「无人」；依据 [Karpathy S3](https://www.latent.space/p/s3) 的 keep-on-the-leash / verifier 角色 + ORD-34 有界多样性立场。
- **推理 · proj-experts · 决定保鲜**：ORD-16 于 2026-05-27 写入，其所依据的外部约束 2026-05（Cursor 3.3）即失效，至今 6 周未被发现——依赖**外部 runtime 事实**的决定没有复查机制，是流程级缺口（DECISIONS 有变更日志但无「事实性前提到期重查」概念）；依据本轮 F1/F2 与 ORD-16 条文对照。

### 方法专属输出（proj-experts）

#### 视角 A · Addy Osmani（loop engineering，评「自动循环」）

**选用理由**：proj 的有界 loop（ORD-31）直接借鉴其框架；评「能否自动循环」用原框架照镜子最公平。

**【已公开立场】**：可靠 agent loop = trigger / goal / tools / verification / memory 五要件齐 + verifier≠maker + 'done' 可判定——[Loop Engineering](https://addyo.substack.com/p/loop-engineering)。

**【模拟推理】**：按五要件打分：goal（DECISIONS 成功标准）✓、tools（5 专家 skill + validation gate）✓、verification（ORD-22 三类 + 外置判定）✓、memory（pipeline-state + artifacts，且是**机读**的）✓——**唯 trigger 只有「人在会话里」一种**。结论：这不是「loop 能力缺失」，是「loop 已具备但没接电源」；接线成本低（状态已外置可再入），属于工程 spike 而非架构改造。

#### 视角 B · Paul Gauthier / Aider（architect-editor，评「省 token」）

**选用理由**：proj-run model-tier 设计的直接灵感来源（ORD-21 来源列）；对双模型分工的经济性有最直接的实践数据。

**【已公开立场】**：architect（强推理模型出方案）+ editor（便宜模型改代码）分工能同时提升质量与降低成本，前提是执行层任务被规约成低歧义指令——[Aider architect blog](https://aider.chat/2024/09/26/architect.html)。

**【模拟推理】**：proj-* 的 ORD-21 五字段闭环 + ORD-22 一行命令可判定 validation 正是「把执行任务规约成低歧义指令」的对应物，**设计层是对的**（EXP-04 中 5/5 templates 一次过 + 0 escalate 是正面证据）。问题在两处：① 小项目 plan 固定成本主导（EXP-04 洞察，算术性的，换什么工具都在）；② 执行层可用的便宜模型选择当时被 runtime 卡死——这一条现在松动了（F1/F2）。所以「省 token 能力」的正确表述是：**机制在、经济性只在足够大的项目成立、且 runtime 前提刚刚变好但未复测**。

#### 视角 C · Karpathy（autonomy slider，评「自动 × 人在环」的张力）

**选用理由**：ORD-31/34 的立场来源；「自动循环」诉求与「GATE 必停」立场的张力需要他这一格来对齐。

**【已公开立场】**：autonomy slider——AI 自主度是滑杆不是开关；人做 verifier；keep AI on the leash——[Karpathy S3](https://www.latent.space/p/s3)。

**【模拟推理】**：用户问「能否自动循环运行项目」时，真实需求大概率不是「无人」而是「**人不用守着**」。当前 proj 只实现了滑杆两端：默认档（人同步陪跑）与高自主档（文本上存在、未 live 验证）。缺的是中间档：**异步值守**——GATE 停点落成待批 artifact + 通知（Slack/webhook），人异步批，loop 自恢复。这一档恰好能同时满足 ORD-34（人在分岔供给多样性）与「自动循环」诉求，且 host 原语（Automations 事件触发 / headless resume）已支持。

#### 收敛（【模拟推理】，非任一专家原话）

三视角同指：**两项能力都是「设计已备、接线未通、证据过期」**——自动循环缺 trigger 接线 + 异步 GATE 机制（非架构问题）；省 token 缺新前提下的复测（ORD-16 过时 + EXP-04 单点外推）。均可用小 spike 闭合，不需要动 INV/ORD 架构层。

## 讨论

### 1. 关切 A：自动循环运行项目的能力——现状 = 框架具备，runtime 不具备

**已具备**（且质量不错）：

- 有界 loop 骨架完整（ORD-31 · EXP-07/07b passed）：PLAN→EXECUTE→VERIFY→GATE?→RE-ROUTE→MEMORY，失败重试有 budget、超限有 escalate、循环有 circuit breaker 有限终止。
- **状态外置 + 机读再入**：`pipeline-state`（ORD-32）+ DECISIONS + docs/pmo artifacts 使任何新会话可从 STATE/CLASSIFY 冷再入——这是可恢复自动化最难的部分，已经做完了。

**不具备**（三个缺口，按阻塞度排序）：

1. **trigger 接线缺失**：loop 只能由「人在会话里发话」触发。host 层原语已存在（F3 Cursor Automations cron/事件；F4 `claude -p` + cron/Routines），proj-* 零接线——没有任何 skill/文档定义「Automation 定时唤醒 → 读 pipeline-state → 续跑到下一 GATE」的协议。
2. **异步 GATE 机制缺失**：GATE 停点假设人在场。人不在场时：停在哪、待批事项落到哪个 artifact、怎么通知人、批准后怎么恢复——全部未定义。Mode β（跨 session message bus）是占位无 runtime，需人工 shuttle。
3. **高自主档未 live 验证**：EXP-07b 的「GATE 自动续跑」是 EXP 授权的模拟，escalate/circuit-breaker 是 harness 证明——高自主档在真实无人环境的行为（尤其失控边界）没有一次实跑。

**定性**：按 ORD-34，「到 GATE 必停」是显式设计立场而非缺陷，所以「全自动无人循环」本就是非目标；但「人异步值守的自动循环」（视角 C 中间档）与既有立场完全相容，是当前真实缺口。→ 候选 EXP-11。

### 2. 关切 B：省 token 能力（高模型规划/评审 + 低模型执行）——现状 = 机制在，经济性证据过期且偏悲观

**已具备**：完整的 model-tier 机制链——proj-plan 出 dispatch manifest（不指定 model）→ proj-run 决策树判定该不该 dispatch → adapter 选 model → ORD-22 一行命令 validation 闭环。EXP-04 正面证据：便宜模型对结构化模板任务质量充分（5/5 一次过 + 0 escalate）。

**证据问题**（三条）：

1. **ORD-16 已过时**（本轮最重要事实发现）：Cursor 3.3 起自定义 subagent 显式 `model:` 被尊重（F1/F2），cursor adapter `model_selectable=false` 不再成立（保留半条：legacy plan 无 Max Mode 仍强制 Composer）。EXP-04 失败模式 F1 的前提「只能调度 Composer Fast」失效——执行层现在可 pin 更强的便宜模型（如 `[composer-2.5]`），且规划/评审层理论上也可反向 pin 高模型。
2. **EXP-04 是单点小项目数据**：「1.58x 不达标」与「≥$10.5 baseline 才 ≥3x」都来自一次小项目试跑的外推；plan 固定成本主导的算术洞察依然成立，但阈值数字在新价目 + 新模型选择下未重算。
3. **claude-code adapter（model_selectable=true）仍未实跑**：EXP-08b 阻塞于「登录不可代办」——但 F4 显示 `claude setup-token` 提供非交互长期凭证，当时的「不可代办」结论可能已有出路（仍需一次交互 setup，但之后无人值守可用）。

**定性**：省 token 能力**不是没有，是「只在足够大的项目上成立」且这个结论本身需要在新前提下复测**。→ 候选修订 ORD-16 + 候选 EXP-12。
