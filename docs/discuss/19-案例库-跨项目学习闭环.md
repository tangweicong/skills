## 用户输入（本轮）

> 那这个项目是不是可以新增一个案例库，用于存放使用这个流程实现的项目的总结，这也算是系统六论中的反馈机制，对吧？那是不是也可以加一个 skill 或者扩展当前的某个 skill，用于自动总结生成案例总结？再用 /proj-shape 开一轮讨论可行性和设计细节。

三个子问题：① 新增案例库（存项目总结）；② 它=系统论的反馈机制？；③ 新增 skill 还是扩展现有 skill 做**自动**案例总结。

## 事实与假设

### 已查证事实（带 URL）

- **F1 · 反馈精确化 = 双环学习（Argyris/Schön）**：单环 = 检测偏差→改动作（不质疑前提）；双环 = 检测偏差→**质疑并修订"治理变量"（信念/规范/政策/激励）**。关键警告："lessons learned that change checklists, not norms" = 假学习；对策 = **重大复盘须至少检视一条治理变量**；且**单环用于例行、双环留给反复/系统性问题**（别处处双环→决策迟滞）。[Argyris 单/双环](https://umbrex.com/resources/frameworks/organization-frameworks/argyris-single-and-double-loop-learning-model/)
- **F2 · 写完没人看 = 头号失败模式**（强证据）：NASA LLIS——"project managers do not routinely use LLIS… outdated, not user friendly, generally unhelpful… underutilized and marginalized" [NASA OIG](https://oig.nasa.gov/wp-content/uploads/2024/02/IG-12-012.pdf)；KM 项目废弃**根因 #15 = 缺"知识蒸馏机制"** [AIS](https://aisel.aisnet.org/cgi/viewcontent.cgi?article=3053&context=cais)；"Enterprises don't fail because they don't capture lessons. They fail because they don't **apply** them… If lessons lack ownership, they decay" [rocketta](https://rocketta.de/en/why-most-lessons-learned-fail-in-enterprises/)。
- **F3 · PMBOK 既有归属 = Manage Project Knowledge + Lessons Learned Register**：MPK 双目的 = **复用旧知识 + 为未来项目产新知识**；主 artifact = Lessons Learned Register（含 ID/日期/阶段/类别/描述/根因/响应/**建议**/估计影响/提供人）；**"持续捕获而非到收尾才写"**（收尾才写的 lesson 泛化、脱上下文、不可行动）。[BrainBOK MPK](https://www.brainbok.com/guide/pm-processes/project-integration-management/manage-project-knowledge) / [PMBOK8 MPK](https://projectmanagement.com.br/manage-project-knowledge/)
- **F4 · 消费路径 = 启动时查阅 + 案例式推理（CBR）**：Ballistic 2.0——"项目经理应在启动阶段**查阅 LL 仓库**…用于更准确定义 charter、甚至帮 sponsor 决定项目是否授权" [IJISPM](https://doi.org/10.12821/ijispm040102)；CBR/CaBMA——AI **检索最相似旧项目并改编其方案**到新项目，从 project plan 捕获 case 并复用生成 plan。[CaBMA AAAI](https://aaai.org/papers/023-iaai04-023-iaai04/) / [KM+AI](https://doi.org/10.30819/5902)

### 推理（三元组标注）

- **推理 · proj-experts · 控制论/Argyris**：案例库确是「反馈机制」——但精确说是**慢/外层双环**（案例→质疑 INV/ORD/skill 这些治理变量→改进流程）。proj-* 的 `INV/ORD` 恰是其"治理变量"，故"案例→升 ORD/改 skill"天然就是双环。但**反馈仅在闭环时成立**：若案例只存不被消费 = 开环 = F2 头号失败。依据 F1+F2+round 13 §视角 A。
- **推理 · proj-experts · PMBOK 归属**：这不是新概念——PMBOK「Manage Project Knowledge」**已被 proj-run 以 ORD-18 承接**，主 artifact = Lessons Learned Register，消费点 = 启动查阅（proj-experts/shape/plan charter）。故**应扩展现有 skill 而非新建**（rule #2）。依据 F3+F4+ORD-18/ORD-10。
- **推理 · proj-experts · YAGNI/最小先行**：现在**0 个已完成案例**（小说 EXP-09 都还没跑）。**先建"案例库容器 + 自动总结 skill"= 为想象规模造基础设施 = 过早抽象**（同 round 17 L2 / round 18 通用化的同型风险）。且 proj-* **已持续产结构化 artifact**（DECISIONS + 变更日志 + EXP result）——一个 case 很大程度是这些的**派生 rollup**，不需重型抽取。依据 rule #2 + F3"持续捕获"。
- **推理 · proj-experts · Prigogine/收敛 3**：写而不用的库是**纯能量沉没**（要喂养、无回报）——负 ROI；只有闭环（被消费、触发改进）才让维护能量正当。依据 round 13 §收敛 3 + F2。

### 待验证 / 未查证

- **U1**：本项目场景下案例库能否真闭环（案例真被下个项目消费并影响决定）？——这是必要性的核心，未验。
- **U2**：跨项目案例的"相似度检索/复用"(CBR) 在仅 1–N 个案例时价值低；规模阈值未知。
- **U3**：本轮单人评审（verifier=maker）→ 候选假设级，不自决。

## 方法专属输出（proj-experts · 4 视角）

### 视角 A · 组织学习 / 控制论（Argyris + Wiener）

**【已公开立场】**：双环学习须检视治理变量；反馈环须闭合 [F1]。
**【模拟推理】**：案例库要成为**真反馈**，设计必须强制**闭环 + 双环**两件事：① 每个案例须能被未来项目**消费**（启动查阅）；② 每个案例须至少**检视一条治理变量**（这条 INV/ORD/skill 是否该改），否则退化为"只改 checklist"的假学习。**不能只设计"存"，必须设计"取"和"改"**。

### 视角 B · PMBOK 知识管理（Manage Project Knowledge）

**【已公开立场】**：MPK 复用+产新知识；LL Register 标准字段；持续捕获；启动查阅 [F3/F4]。
**【模拟推理】**：本能力**已有归属**——proj-run ORD-18（MPK）+ proj-plan ORD-10（Close）。案例库 = 这条线的 artifact。**消费点**落在 proj-experts/shape/plan 的启动（charter/ORD 前查阅相似案例）。→ **扩展这几个 skill 的既有职责**，案例库是新 artifact 类型 + 两个挂钩（收尾捕获 / 启动消费），**非新 skill**。

### 视角 C · 极简 / YAGNI 守门人

**【已公开立场】**：≥2 实例才抽象；不为单次造 skill [rule #2]。
**【模拟推理】**：拆三件事分别判 YAGNI——① **案例模板 + 目录**：低成本，但**等第 1 个真案例**（小说）再建，别先搭空库；② **消费路径**：真价值所在，但只有 ≥2 个项目才看得出复用效果（U2）；③ **自动总结 skill**：**最该缓**——0 案例、无重复模式、且全自动撞 F2"脱上下文泛化总结"+ round 18 maker=verifier。**结论：现在不加 skill；先手工产 1 案例 + 定闭环路径。**

### 视角 D · 派生而非另写（承接 round 17 L1 思想）

**【模拟推理】**：proj-* 管理的项目**已有结构化 DECISIONS + 变更日志 + EXP result**——一份 case summary 很大程度可从这些**半自动派生 rollup**（决定/EXP 成败/降级触发/关键 trade-off），AI 起草 + 人审即可。所以"自动总结"**可行且不贵**，但应是**扩展 proj-plan Close 的派生动作**，不是独立 skill。

## 讨论

### 1. 回答三个子问题

- **① 案例库**：值得，**但价值系于闭环**（被消费），不系于存储。是 PMBOK 的 Lessons Learned Register / case base。它也正是 round 18「小说经验怎么回流」的**制度化版本**——小说 EXP-09 result = 库里第一个案例。
- **② 反馈机制？**：✅ 对，且精确 = **慢/外层双环学习**（案例→质疑 INV/ORD/skill）。但⚠ 写而不用 = 开环 = 头号失败（F2）。
- **③ 新 skill 还是扩展 + 自动？**：**扩展**（proj-run MPK / proj-plan Close 已owns），**不新建 skill**（YAGNI）；**自动 = AI 从结构化 artifact 派生草稿 + 人审**，非全自动，非现在。

### 2. 拆成 3 个可分别决策的件（避免一锅端）

| 件 | 内容 | 成本 | 何时做 |
|----|------|------|--------|
| **D1 捕获** | 案例模板（PMBOK LL Register 字段：ID/日期/项目类型/类别/做了什么/根因/**建议**/影响/治理变量检视）+ `cases/` 目录 | 低 | 第 1 个真案例（小说 EXP-09 result）出现时 |
| **D2 消费（真价值）** | 闭环路径：新项目在 proj-experts/shape/plan **启动时查阅相似案例**（CBR 雏形=人工挑，不上检索引擎）；案例须被引用过才算"活" | 中（设计为主）| 与 D1 同期定义，第 2 个项目验证 |
| **D3 自动化** | 扩展 proj-plan Close（或 proj-run MPK）：AI 从 DECISIONS+变更日志+EXP result **派生**案例草稿 + 人审 | 中 | **缓**——≥2–3 案例显出可重复模式后 |

> **关键纪律（防 F2 写而不用）**：D1 不先于 D2 设计；**消费路径没想清楚就不建库**。且每案例强制"双环字段"（至少检视一条 INV/ORD/skill 该不该改 · F1）。

### 3. 推荐序（不替你拍板）

1. **现在**：定**案例模板 + 闭环路径**（D1 schema + D2 何时查阅/谁消费），但**先不建空库、不加 skill**。
2. **小说 EXP-09 跑完**：手工产**第 1 个案例**（用模板，AI 起草+你审）——验证"派生 rollup"可行、字段够用。
3. **第 2 个项目启动**：真去查阅案例 1 → **验证闭环**（案例是否影响了决定）= EXP-10 成功信号。
4. **闭环证成 + ≥2–3 案例**：才扩展 proj-plan Close 做 D3 自动派生 + 评估是否需要 CBR 检索（U2）。

### 4. 与既有的关系

- 案例库**不是新机制**：proj-run ORD-18（MPK）+ proj-plan ORD-10（Close）已owns，本轮是**给它定 artifact + 闭环挂钩**。
- 与 round 18 同一根线：单项目回流（round 18）→ 制度化为跨项目案例库（本轮）。
- 与 round 13 自洽：双环 = 控制论反馈（视角 A）；闭环才让维护能量正当（收敛 3）。
