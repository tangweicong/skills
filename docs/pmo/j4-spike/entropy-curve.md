# J-4 内部实测：`pipeline-state.status` 熵曲线与 ORD-32 两半约束的差异（2026-08-27）

> 父 agent 用 git 历史实测，**独立于** J-4 争议轮三视角（它们拿不到本数据）。
> **口径更正留痕**：初测用 `awk length($0)` 得 1987，实为**字节**；改用 Python `len(str)` 得 **1195 字符**。争议轮的独立核对（报 1,185）先于本更正抓到了该误差——一次有效的外部校正。

## 二、关键对照：同一条决定（ORD-32）的两半，命运相反

ORD-32 同时确立了两条约束：

| 约束 | 写在哪里 | 形式 | 有无机检 | 51 天后 |
|------|---------|------|---------|---------|
| **当前态摘要 ≤12 行** | **章节标题内**：`## 当前态摘要（活动头部 · ≤12 行 · …）`——编辑该节时必然看见 | **可数的数字** | **无** | 9 → 10 行，**零违反** |
| **`status` 「仅索引不复制条文」** | **ORD-32 条文里**（文件另一处，编辑 yaml 块时看不见）| **定性措辞** | **无** | 284 → 1195，**4.21x** |

**两者都没有机器检查**（`scripts/validate_skills.py` 的 C1 只校验 `pipeline-state` 三字段是否存在 + `stage` 是否在枚举内 + `pending_exp` 是否为 list，**完全不看 `status` 长度**）。

→ **差异不在「有没有 validator」，在于约束是否以「可数的数字」出现在「使用点」上。**

## 三、自指证据：散文式自我提醒无效

本会话前几轮，父 agent 在每次追加 `status` 时都写了自注「**本 status 字段已逾 1500 字符…修复前刻意不再扩写**」——而该自注**本身就写在 `status` 字符串内部**，给它又加了约 60 字符，且下一轮照样扩写。

**结论**：写在使用点上的**散文提醒**不起作用；写在使用点上的**可数数字**（≤12 行）起作用。差别不是「有没有提醒」，是「提醒能不能被一眼判定真假」。

## 四、与争议轮三视角的关系

本数据**独立收敛**于争议轮 §收敛 第 1 条（「ORD-32 不是失败，是不完整——给一个容器设了界，却把相邻容器留成无界的，压力全部迁移到唯一没有上限的槽位」），并为其补上**机制层解释**（为什么是那一半活下来）。

同时它对争议轮 §分歧 第 3 行（长度界 vs 类型界）构成**部分裁决**：存活下来的那条约束（≤12 行）**正是一条长度/计数界**——说明长度界并非天然会被规避，前提是它出现在使用点且可一眼判定。→ 支持「两者都要」而非二选一。
