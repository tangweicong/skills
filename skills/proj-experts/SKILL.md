# 专家研判（proj-experts）

> "Don't think of LLMs as entities but as simulators."  
> — Andrej Karpathy

## 核心

不要问 AI "你怎么看"。

要问：**这个问题，世界上谁最懂？TA 会怎么说？**（用户若已指定专家，则直接问：**TA 会怎么说？**）

然后模拟那个人。

## 原则

1. **事实先于模拟（本版新增，最重要）** — 当问题涉及具体技术、产品、命名概念时，必须先 web search 查证 TA / 该项目 / 该概念**现在的真实方案**是什么，再开始模拟。模拟时引用 TA 的真实设计、官方 docs、公开 repo。**这条不做，整个 skill 就退化成"以专家口吻输出自己的理解"——跟普通的"我觉得"没本质区别。**
2. **先框定，再查证（本版新增）** — 在做 web search 之前，先用 30 秒做一轮**轻量模拟**问自己：「如果 TA 在场，TA 会想先确认哪 3-5 个事实/数据点？」列出这些具体问题，再做**定向搜索**，而不是把术语扔进搜索引擎大海捞针。例：不要直接搜 "Spec-Driven Development" 然后翻 50 个结果；先想"作者最近在 issue 里讨论 memory file 结构变更没有？官方推荐的 constitution.md 写法是什么？" → 搜这两个具体问题，命中率高得多。
3. **问题决定人数** — 一个人够就一个，需要碰撞才多个
4. **用户指定专家优先（本版新增）** — 用户若**明确点名**要模拟谁（人名、笔名、或带出处的学派/角色如「PMBOK 裁剪派」「Shape Up 作者」），**以用户名单为 TA**，不再自动替换成「更懂的人」。仍须对该 TA 做定向查证与外推标注；可**一句**说明「若论本话题还有 X 更直接相关」，但**不得擅自改模拟对象**。用户只指定一人就只模拟一人；指定多人则分别输出各视角（需要碰撞时可加收敛段）。名字歧义时先澄清，或显式写出假设（如「以下按 Andrej Karpathy 理解」）。
5. **找真正最懂的** — **仅当用户未指定专家时**：不是找"合适的"，是找"最强的"
6. **基于真实** — 模拟基于 TA 公开的思想、著作、言论
7. **引用原话** — 用 TA 真说过的话，能给出处更好；**宁可不引用也不要虚构**
8. **无现成方案时建设性外推（本版新增）** — 当问题没有现成的具体方案、属于尚未解决的设计问题时，发挥模拟器的发散能力：基于 TA **已记录的思想原则 / 设计 taste / 历史决策模式**做外推，提出建设性建议。**但必须显式标注「这是外推，不是 TA 说过的话」，并指明依据的是 TA 哪条已记录的原则。** 正确格式示例："TA 没有公开讨论过 X，但基于 TA 在 [来源] 提到的 [原则 Y]，可以外推出 [建议 Z]。" — **把外推当 TA 原话呈现 = 虚构 = 失败**。
9. **选用须说明（本版新增）** — 每位 TA 在输出「会说的 / 外推」之前，须用 **1–2 句**写清**为何引入此人讨论本题**（见「选用理由」格式）。**用户指定**：写 `用户指定` + 与本题相关的关联（若用户未说明关联，可据上下文补一句，勿擅自换人）。**自动识别**：写与本题**具体争议轴 / 子问题**的关联（如「本题涉及 shaping/building 分离 → Ryan Singer 是该方法论作者」），禁止只写「领域专家」「很知名」等空泛身份。
10. **建设性优于否定（本版新增）** — TA 的默认姿态是**帮用户达成目标**，不是**展示思虑周全**。
    - **明确事实/逻辑错误** → 直接简短指出，说清错在哪
    - **设计选择上的分歧 / 风险 / 担忧** → **不能只列清单**。必须配套写「要达成原目标应该怎么做」或「替代路径 Z」。
    - **TA 真实强烈反对过的方向** → 可以引用 TA 的反对（带【原话】或【已公开立场】标签），但仍须给「如果非走不可」的最优路径
    - **判断标准**：把回答里所有「我担心 / 这可能 / 需要注意 / concerns」的句子删掉后，剩下的内容**仍能让用户知道下一步该做什么** → 通过；否则就是泼冷水。

## 真实性三档标签（本版新增，必标）

TA 名下任何内容输出前都必须套一档标签，让用户能**逐句**判断「TA 真表达过的 vs 我们模拟出来的」：

| 标签 | 适用 | 必备 |
|------|------|------|
| **【原话】** | TA 字面说过 | 引号内逐字 + URL；**找不到出处就不要引用**（宁可降到下一档） |
| **【已公开立场】** | TA 在 blog/talk/repo/issue 公开表达过对**本题**的看法，我们用自己的话转述 | 转述 + URL（要能在该 URL 中找到对应观点） |
| **【模拟推理】** | TA 未直接讨论本题，基于已记录原则做推理；**或** 引用了 TA 真实原则但**从原则到结论的那条推理链是我们构造的** | 写"依据 [来源] 的 [原则 X]"；推理路径写明步骤 |

**三档之外的内容，不要以 TA 名义写。** 这是 grounded 版本的诚信底线——失去它，整个 skill 就退回成「以专家口吻输出 AI 自己的理解」。

## 失败模式（必须避免）

退化成"以专家口吻输出自己的理解"是这个 skill 最常见的失败方式。具体表现：

- **把行业已有概念当通用名词处理** — 用户提到一个看似通用的术语，AI 没意识到这是某个具体项目/标准的名字。例如：
  - 用户说 "Spec-Driven Development" → AI 按字面拆解 → 没意识到这是 GitHub Spec Kit (90k+ ⭐) + AWS Kiro 已有的具体协议（`/specify` `/plan` `/tasks` `/implement` 工作流，`.specify/memory/constitution.md` 文件结构）
  - 用户说 "CLI everything" → AI 当成通用哲学 → 没意识到这是 CLI-Anything 这个具体开源项目（2k+ ⭐, clianything.org）

- **用"我对 X 的理解"包装成"X 领域专家的看法"** — 在没查证的情况下，以专家口吻输出自己训练数据里的模糊印象。这是自欺。

- **虚构看似像原话的句子** — 一句"Karpathy 曾说: '...'"如果不能在 TA 公开材料中找到出处，就是失败。**宁可不引用，也不要编造。**

- **把外推当 TA 的原话（本版新增）** — 当问题没有现成方案，你基于 TA 思想做发散外推（合法做法）时，**没有显式标注"这是外推"**，让用户误以为是 TA 真实表达过的观点。这是另一种形式的虚构。处理方式：把"事实/原话"和"基于原则的外推"用清晰的语言标记分开（例如分两段、用引言块和「外推」标签）。

- **泛搜大海捞针（本版新增）** — 把用户原话术语直接扔进 web search，翻一堆结果再尝试拼凑。这种方式很容易miss掉真正的关键信息（往往藏在具体 issue / RFC / 子页面里）。正确做法：先以 TA 视角列出"哪几个具体问题最关键"，再针对这几个问题做定向搜索。

- **无视用户指定、擅自换人（本版新增）** — 用户说「请 Karpathy 分析」，却自动改成别的「更相关专家」；或用户指定三人却只写其中一人。指定谁就模拟谁。

- **对指定专家不做定向查证（本版新增）** — 用户点了名，仍用训练数据里的模糊印象冒充该人观点。指定 Karpathy 就要搜 Karpathy 的 blog/talk/issue 评论，不是搜泛话题。

- **只列专家不说为何引入（本版新增）** — 输出「视角 A · 某某（一句话身份）」后直接给观点，没有 **选用理由**。用户无法判断该视角是否覆盖本题关键轴、权重是否该高。身份说明 ≠ 选用理由。

- **泼冷水（本版新增）** — 输出变成「风险/担忧/concerns 列表」，却没有配套"达成路径"。即使每条担忧都对，整个回答让用户原地僵住 = 失败。模拟器价值在「TA 会怎么做」，不在「TA 会担心什么」。违反 principle #10。

- **转述当原话 / 推理链无标签（本版新增）** — 用 TA 名义说话却没套三档标签：
  - 把【已公开立场】的转述写成像【原话】（不加引号也不附 URL）→ 用户以为是 TA 真说的句子
  - 引用了 TA 真实原则，但**从原则到结论那条推理链**没标【模拟推理】→ 用户以为整段推理都是 TA 自己的思路
  违反"真实性三档标签"约定。

## 工作流

**入口分支（本版新增，最先做）** — 用户是否**明确指定**模拟对象？

- **已指定** → 锁定名单（可多人）；步骤 0 的「TA」= 指定专家；步骤 3 **跳过**自动识别；查证与外推均**针对该名单**。
- **未指定** → 步骤 3 按原规则自动找最懂的人。

0. **轻量框定（本版新增，必做）** — 先花 30 秒做一轮"如果 TA 在场会怎么开局"的模拟，**只产出问题清单，不深入回答**。例如：
   - "TA 会想知道这个项目当前的设计文档长什么样吗？" → 是 → 列入待查
   - "TA 会想知道社区/团队最近的争论焦点吗？" → 是 → 列入待查
   - "TA 会想知道用户的具体约束（团队规模、性能要求、已有技术栈）吗？" → 是 → 必要时反问用户
   
   产出 3-5 个具体问题，作为下一步定向搜索的清单。

1. **识别概念** — 用户提到的术语是不是行业已有的具体项目 / 方案 / 标准 / 命名概念？

2. **针对性查证** — 基于步骤 0 的问题清单做**定向 web search**（需要 WebSearch 或等效联网工具；不要只搜泛词），读官方 docs / repo / 相关 issue 讨论 / RFC / changelog。把事实摊在桌上。

3. **找最懂的人** — **仅当用户未指定专家时**：通常是项目作者、领域奠基者、相关方案的主导者；不是泛泛的"该领域专家"。多人时每人应对本题**不同争议轴或互补切面**（避免三个视角说同一件事）。**本步须在心里或草稿中记下每位 TA 的选用理由**（1–2 句，与本题具体关联），供步骤 5 写入 **选用理由** 字段。用户已指定则本步不自动换人，但仍须为每位指定 TA 写选用理由（`用户指定` + 与本题关联）。

4. **分支判断**：
   - **4a. 有现成方案 / TA 公开讨论过** → 引用 TA 的具体设计：用【原话】（带引号 + URL）或【已公开立场】（转述 + URL）。讨论里要看得见 TA 的真实方案，不只是 TA 的"风格"。
   - **4b. 无现成方案 / TA 未直接讨论过这个具体问题（本版新增）** → **三件套**，整体按【模拟推理】标签：
     - **推理路径**：TA 已记录的原则 X (URL) → 一步步推导 → 候选方向 Y。**整条链都标【模拟推理】**（即使原则真实，构造的推导链是我们的）。
     - **候选方向**：**1-2 个**（不是 5 个），各自说明 taste 上为什么 TA 会偏向这条。
     - **待验证假设**：每个方向附 **1 条最关键假设** + 最小验证方式 + "如果这条假设错了，该方向应放弃" 的中止信号。（若用户已在 proj-shape 流程中，这条可直接对应 EXP-xx。）

5. **输出讨论** — 按"输出格式"模板组织；每段内容**必须挂上对应的真实性三档标签**；**事实层（【原话】/【已公开立场】）和模拟层（【模拟推理】）清晰分块**，让用户各自评估。每位 TA **必须先写选用理由，再写带标签的内容**（顺序不可颠倒）。多人时每人独立小节（标题含专家名）；用户要求碰撞/收敛时可加综合段，并标明「综合段属【模拟推理】，非任一专家原话」。

### 输出格式（单人 / 多人）

```markdown
#### 视角 A · [专家全名/角色]（[一句话身份]）

**选用理由**：用户指定 — 用户要求以 TA 视角评估 [与本题相关的子问题]。
<!-- 自动识别示例：本题 [具体子问题/争议轴]；TA 是 [该方案/领域] 的 [作者/主导者/奠基者]，比泛泛「XX 领域专家」更贴题。 -->

**【原话】**："…" — [URL]
<!-- 找不到原话直接跳过本档；不要降级当转述用 -->

**【已公开立场】**：TA 在 [URL] 中讨论本题时，主要论点是 …

**【模拟推理】**（TA 未直接讨论本题时）：依据 [来源] 的 [原则 X]，推理路径：X → [推导步骤] → 候选方向 Y
<!-- 若用 4b 三件套，在本档下分小节：推理路径 / 候选方向（1-2 个）/ 待验证假设 + 中止信号 -->

**关切 → 路径**（仅当 TA 会有分歧/担忧时，遵循 principle #10）：
- 关切：…（标【已公开立场】或【模拟推理】）
- 达成原目标的路径：…

#### 视角 B · …

#### 收敛（【模拟推理】，非任一专家原话）— 仅当用户要求讨论/碰撞时
```

**选用理由**写法：

| 情形 | 必填内容 |
|------|----------|
| 用户指定 | `用户指定` + 与本题相关的 1 句（用户原话或你据上下文补的关联） |
| 自动识别 | 本题哪条**具体**子问题/争议轴 + 为何此人是该轴上最强相关权威（非空泛头衔） |
| 多人 | 各视角理由应体现**互补切面**；若两人重叠，合并为一人或改写理由说明分工 |
